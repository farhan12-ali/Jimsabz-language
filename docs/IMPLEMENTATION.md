# Implementation and report coverage — Studio 0.9.0

The master report remains the language design input. The latest user requirements supersede the old separate-page UI: code and the compiler journey stay in the main editor; Run opens a separate console/game window. No prebuilt game catalogue or assets are included.

## Architecture

- `src/` is the native C++17 compiler, typed stack VM, software 2D/3D renderer, networking, executable bundler, and loopback Studio host.
- `studio/core/` is an actual browser lexer, parser, semantic analyzer, JBC2 emitter and asynchronous stack VM. It compiles current user code in a dedicated worker. Stop terminates the worker, including a pending input wait or loop.
- `studio/app.mjs` implements ordinary folders, file editing, IndexedDB working copies, explicit disk/file exports, compiler inspection, completion and the agent UI.
- The browser and C++ implementations share the JBC2 opcode and binary format. Browser-generated bytecode has been executed successfully in the native VM; these are separate implementations, so this is interoperability evidence, not proof of identical behavior for every possible program.
- `studio/agent/` and `training/` contain the local statistical agent, Jimsabz-only curriculum, trainer and curated evaluation. Code builders are parameterized and compiler checked. No general-purpose code LLM was trained.

The desktop launcher serves only the packaged UI on 127.0.0.1, rejects cross-host requests, restricts paths to the studio directory, opens the default browser and exits after heartbeat expiry. No remote AI or runtime package download occurs. The CLI and exported applications remain native, independent of this UI host.

Typed cells preserve left-to-right evaluation and container aliases. Constants freeze their shared contents. Arithmetic and array access are checked; runtime faults can be caught with azmai/pakar. Bytecode has bounded fields, source positions, functions, class layouts, asset references and CRC32. Standalone exports append JBC2 and literal asset bytes to the native runtime. Editable .jimsabz source, .jbc/.jjimsa bytecode, and native .exe exports have different portability requirements described in README.

## Browser/native runtime differences

The browser preview supports terminal programs, typed data, control flow, functions, classes, modules, local workspace file I/O, actors, basic physics, timers, collisions, input, sprites, OBJ/primitives and a perspective game view. It uses Canvas 2D for 2D drawing and depth-sorted projected triangles for 3D. The native renderer uses a pixel framebuffer and a Z buffer. The browser preview does not provide native UDP shabak networking, OS speech, full native depth/texture rendering or target-hardware performance certification. Audio in the browser is subject to browser playback permissions. Dynamically calculated asset paths are not automatically discovered for export. Only literal referenced assets are embedded; folder ZIP includes every file.

## Non-functional requirements

| Requirement | Current evidence |
| --- | --- |
| NFR-01 No external runtime dependencies | Windows binaries import OS DLLs only; C++ support libraries are linked statically. Studio uses the installed browser; Python and Node.js are optional development/test tooling |
| NFR-02 60 FPS, 300 entities/500 particles | Both stress cases are measured in `build/benchmark-*.json`. A 16.67 ms worst-case limit is not certified; the 3D run can exceed it |
| NFR-03 400-line compile/launch under 50 ms | Compilation is measured separately in `build/benchmark-compiler.json`. Native GUI/asset launch latency is not certified |
| NFR-04 Under 64 MB/bounds safety | Bounds/overflow checks and measured Linux stress-process RSS are provided. There is no universal 64 MB process-memory cap |
| NFR-05 Non-blocking audio | Asynchronous Windows calls are implemented; sub-millisecond timing is unmeasured |
| NFR-06 Asset/input fault tolerance | Missing audio falls back to synthesis; invalid input is caught in regression tests. Windows fallback playback needs desktop testing |
| NFR-07 Complete game in under 85 lines | Blank starters are supplied; a simple racing request generates 54 readable lines of Jimsabz |
| NFR-08 Clear diagnostics and voice | Compiler/runtime error locations and phase display are implemented; full native voice coverage and complete live squiggles remain |

## Studio 0.2.1 separate execution window

`studio/run.html`, `run.mjs` and `core/run-window.mjs` implement the separate run window. The visible window drives game ticks, avoiding a background editor timer. Origin, source window, session and run IDs guard cross-window commands. Closing output cancels pending input and execution; code stays open. The agent panel is optional, and initial page load does not launch a program or popup.


## Studio 0.8.0 file management

The explorer has real nested/empty folders, file and folder context menus, rename, delete confirmation and persistent Trash. The workspaces object store retains deleted workspace tombstones; regular records retain deleted file/subfolder snapshots. Restore validates all paths before changing live data. A stale tab cannot write an undeleted version over a tombstone. No IndexedDB schema upgrade is needed. Original disk folders are unchanged; renamed/moved workspace files detach old disk handles. Relative module references are updated using lexer tokens; asset string references require manual edits.


## Studio 0.9.0 presentation workflow

The Language examples panel supplies seven editable source programs and runs fresh compiler/VM checks with sample inputs in a separate worker. The full marksheet combines variables, conditions, loops, functions, arrays and objects; input counts are chosen at runtime. These ordinary programs do not preload games or replace the language compiler. Closing the panel stops unfinished checks. The Windows rehearsal command uses the bundled native runtime and golden output files; it still requires actual Windows execution.
